# 原子事实系统下一轮迭代方案

日期：2026-08-30
状态：待确认
适用范围：GEOFlow 管理端、原子事实库、AI 质检链路

## 评审结论

建议调整下一轮的升级重心。现有 Phase 1 至 Phase 2 已经具备事实库、标准值、证据、版本、AI 生成、人工审核、发布和恢复等底层能力，后端安全边界也较完整。当前主要缺口集中在三处：入口难发现，治理过程难完成，原子事实尚未成为正式质检链路的一部分。

下一轮按四个可独立合并的迭代推进：

1. 建立独立的原子事实工作台，完成生成、审核、发布的产品闭环。
2. 补齐适用性判断与类型化比较，先进入影子质检。
3. 在文章质检结果中解释命中、冲突、回退和事实版本，完成正式上线前评测。
4. 启用混合质检灰度，稳定后再把活动事实用于文章生成约束。

正式质检接入排在工作台和比较器之后。这样可以保证进入质检的事实已经经过审核、证据校验和发布，质检结果也能向管理员解释。

## 当前实现已经解决的部分

当前代码已经覆盖以下能力：

- 一个知识库对应一个原子事实库，事实、标准值、证据和发布版本有独立模型。
- AI 生成支持初次生成、补充生成和陈旧刷新，单次目标数量可以配置。
- 生成任务有活动运行唯一约束、请求幂等、源哈希校验、取消、冲突处理和失败状态。
- 发布时会检查事实审核状态、值审核状态、冲突、证据有效性和关键数值的主要证据。
- 发布版本不可变，恢复会创建新版本，知识切块变化后可以把服务状态标记为陈旧或不可用。
- 生成弹窗已经支持后台执行、轮询、焦点恢复和基础无障碍提示。
- 4 篇真实文章的对照测试中，原子事实方案节省 40.81% Token，平均耗时降低 22.77%，并识别出知识库整段质检漏掉的版本冲突。

这些能力可以继续使用，本轮不重建数据模型，也不替换现有 Laravel AI SDK 调用方式。

## Review 发现的问题

### P0：产品闭环仍未完成

**入口埋在知识库详情页底部。** 用户需要经过知识库内容编辑区才能看到原子事实，页面缺少事实数量、待审核数量、冲突数量和当前生效版本等入口信息。知识库列表也没有可见状态。

**一个页面承担过多任务。** 当前局部模板同时放置手工新增、AI 生成、事实列表、标准值、证据、合并、拆分、运行历史、冲突处理、版本恢复和发布。它适合验证接口，难以支撑 20 至 200 条事实的持续治理。

**状态使用开发字段。** 页面直接显示 `review_required`、`unavailable`、`stable_key`、`lock_version`、原始 JSON、chunk ID、`initial` 和 `supplement`。管理员需要先理解内部实现，才能判断下一步操作。

**审核动作缺少顺序。** 事实和标准值分别审核，证据又需要单独绑定。页面没有审核进度、下一条、退回原因、来源摘录、重复候选建议和发布准备度，用户很难确认一条事实是否真的完成。

**发布按钮缺少发布前说明。** 只要存在启用事实，页面就显示发布按钮。后端会严格拒绝不合格内容，前端没有提前告诉用户还差哪些条件，容易形成反复提交和报错。

### P0：原子事实尚未进入正式质检

当前 `ArticleAiQualityInspectionService` 仍使用知识库检索、动态事实抽取和通用模型判断。已有 `AtomicFactComparator` 只覆盖基础数字、精确文本和包含关系，也没有进入正式评分器。基准测试出现了“问题列表发现冲突，最终决策仍通过”的不一致，说明比较结果与评分门禁之间还缺少统一契约。

### P1：异步生成体验缺少恢复与控制

生成状态接口已经返回进度、候选数和冲突数，弹窗没有充分呈现这些信息。刷新或重新进入页面后，前端不会自动恢复活动任务。取消能力存在于后端，弹窗中没有直接入口。完成后的“去审核”会整页刷新并定位锚点，无法把用户带到明确的待审核队列。

### P1：页面查询会随事实量增长

知识库详情目前一次加载全部事实、全部值和证据计数，再在 Blade 中渲染完整管理界面。事实量达到 100 至 200 条后，HTML 体积、查询内存和操作密度都会上升。生成运行已经限制为最近 10 条，这个模式应扩展到事实、冲突和修订列表。

### P1：状态语义缺少统一投影

底层存在两套状态：工作流状态包含 `idle`、`generating`、`review_required`、`failed`；服务状态包含 `unavailable`、`ready`、`stale`。这套设计合理，页面需要把组合状态转换成用户可执行的说明，比如“待审核 19 条”“已有 v2 服务，工作区有新改动”“来源已更新，需要刷新证据”。直接展示原值会让用户误解 `review_required + ready` 这类正常组合。

### P2：质检解释与运营指标缺失

文章页只能看到总分、结论和通用问题。管理员无法确认本次使用了原子事实、知识库检索还是混合回退，也看不到事实版本、文章原句、标准答案、比较方式和证据出处。知识库侧也缺少覆盖率、冲突率、回退率、Token 节省和质检命中等效果数据。

## 产品目标

这一轮完成后，用户从知识库详情进入原子事实库，可以清楚完成下面这条路径：

```text
知识库详情
  -> 查看事实库准备度
  -> AI 生成或手工新增
  -> 审核标准答案与来源
  -> 处理冲突和重复项
  -> 发布不可变版本
  -> 在文章质检中查看事实命中与差异
  -> 根据覆盖率和错误数据继续补充事实
```

体验目标如下：

- 用户从知识库详情最多两次操作即可启动生成。
- 生成完成后，一个主按钮直接进入待审核队列。
- 任意页面都能看到当前生效版本、工作区状态和下一步建议。
- 常用操作只展示业务语言，技术字段放入“技术详情”。
- 事实量达到 200 条时，页面仍可通过搜索、筛选、分页和批量操作管理。
- 文章质检结果可以回答“用了哪些事实、哪里冲突、为什么回退、哪个版本生效”。

## 推荐的信息架构

### 知识库列表

每个知识库增加一项轻量状态：事实总数、生效版本和准备状态。状态只有四种用户语言：未建立、待审核、可用于质检、需要更新。点击后进入原子事实工作台。

### 知识库详情

在页面标题区增加“原子事实库”入口。知识库内容区域只保留一张摘要卡，展示：

- 生效版本和发布时间。
- 事实总数、待审核数、冲突数、陈旧证据数。
- 一句状态说明和一个随状态变化的主操作。

主操作按状态选择：

| 当前状态 | 主操作 | 辅助说明 |
|---|---|---|
| 未建立 | AI 生成事实 | 从当前知识库提取标准答案 |
| 生成中 | 查看生成进度 | 离开页面后任务继续执行 |
| 待审核 | 继续审核 | 显示剩余数量 |
| 可发布 | 检查并发布 | 显示发布影响范围 |
| 已发布 | 管理事实库 | 显示当前 vN |
| 来源陈旧 | 刷新事实证据 | 当前质检已自动回退 |

### 独立原子事实工作台

新增管理端页面 `admin.knowledge-bases.facts.index`。该页面承载持续治理，知识库详情不再渲染完整事实编辑器。

页面结构：

1. 顶部状态区：知识库名称、生效版本、工作区版本、服务状态和主操作。
2. 指标区：全部事实、待审核、冲突、陈旧证据、已用于质检次数。
3. 筛选区：待审核、全部、冲突、已发布版本，支持关键词和状态筛选。
4. 工作区：桌面端使用事实列表加详情面板，移动端使用单列列表和独立详情。
5. 发布准备区：持续显示未满足条件，全部通过后开放发布确认。

事实列表优先展示指标名称和标准答案。主体、谓词、值类型、稳定键和锁版本放到次级信息或技术详情。每一行显示来源健康、审核状态和是否存在历史值。

详情面板按用户审核顺序组织：

1. 指标名称和适用对象。
2. 标准答案及结构化值。
3. 生效时间、范围和比较规则。
4. 来源摘录与原文位置。
5. AI 生成说明、重复项和冲突提示。
6. “通过并查看下一条”“修改后通过”“退回”三个主要动作。

批量通过只对证据有效、无冲突、未被人工修改的候选开放。系统显示选中数量并要求确认，不提供无条件的一键全部通过。

## 生成体验

继续使用居中模态框处理生成配置和运行进度，配置文案改为业务语言。

生成前：

- 系统根据事实库状态自动选择初次生成、补充生成或刷新证据。
- 目标数量提供 20、50、自定义三个选择。
- 默认沿用知识库可用的 AI 模型，模型切换收进高级选项。
- 显示知识切块准备度、当前事实数、预计批次数和“现有生效版本不会受影响”。

生成中：

- 展示已处理批次、目标数量、候选数、冲突数、耗时和下一次检查状态。
- 提供“后台运行”和“取消任务”。取消后保留已经安全写入的候选，并明确说明结果。
- 页面刷新、返回工作台或重新登录后，自动恢复活动运行。
- API 增加 `cancel_url`、模式、目标数量、已完成批次数、总批次数、耗时和可操作错误信息。状态投影移入 Presenter 或 Resource。

生成完成：

- 主按钮显示“审核 N 条候选”。
- 冲突单独显示数量，进入冲突筛选。
- 生成失败时显示失败阶段、可重试条件和安全保留的数据。

## 发布与版本体验

发布动作改为准备度检查加确认弹窗。准备度包含：

- 启用事实均已审核。
- 启用标准值均已审核。
- 冲突已处理。
- 必需证据存在且仍指向当前知识切块。
- 关键数值有主要证据。
- 时间区间和比较规则有效。

确认弹窗展示新版本号、事实数量、相对当前版本的新增、修改、停用数量，以及发布后的使用范围。发布完成后显示“vN 已发布”，正式质检灰度开启前补充“当前用于影子质检”的状态说明。

版本历史增加变更摘要和恢复确认。恢复仍创建新版本，页面明确显示来源版本和当前知识源是否匹配。

## 质检架构

推荐采用原子事实优先、逐条回退的混合链路。只有活动版本为 `ready` 的知识库进入原子事实通道。没有活动版本、来源陈旧、候选冲突、范围不完整或事实未覆盖时，相关主张进入现有知识库质检。

```text
文章内容
  |
  v
ArticleAtomicClaimExtractor
  |
  +------------------------+
  |                        |
  v                        v
FactManifestCompiler    未覆盖或有歧义
  |                        |
  v                        v
FactMatcher             现有 EvidenceBuilder
  |                        |
  v                        v
Applicability          知识库检索与模型核验
  |
  v
ValueNormalizer -> AtomicFactComparator
  |                        |
  +------------+-----------+
               v
     ArticleAiQualityResultAggregator
               |
               v
   ScorerV2 -> ArticleAiQualityCheck -> 管理端解释
```

服务边界：

- `ArticleAtomicClaimExtractor` 负责分句、数字和日期候选、引用及否定角色，不做最终真值判断。
- `FactManifestCompiler` 只读取活动且健康的不可变 revision，并按库哈希缓存。
- `FactMatcher` 负责主体、谓词和别名召回，语义相似度只用于生成候选。
- `KnowledgeFactApplicability` 判断时间、范围、单位、币种和比较运算符是否可比。
- `KnowledgeFactValueNormalizer` 归一化中文数字、数量级、日期、百分比和单位。
- `AtomicFactComparator` 产生 `supported`、`contradicted`、`not_covered`、`ambiguous`、`stale` 或 `conflict`。
- `ArticleAiQualityResultAggregator` 把原子事实问题和现有质检问题合并，再由同一个评分器产生分数与门禁。

## 比较器契约

持久层继续使用现有 `string`、`integer`、`decimal`、`number`、`date`、`boolean`、`url`。比较方式从值类型、单位和 `comparison_policy_json` 推导，避免为了每一种业务口径扩张数据库枚举。

首轮必须覆盖：

- 整数、小数、中文数量级和千分位。
- 百分比、百分点、比例和容差。
- 币种一致性，首轮不做实时汇率换算。
- 日期、年份、月份和有效区间精度。
- 布尔值与有限枚举。
- URL、路径和版本号的标准化比较。
- 文本别名、空白和标点归一化。
- “约”“至少”“至多”“超过”“介于”等运算符。

数值与日期优先使用确定性比较。文本候选在规则无法确认时，汇总为一次结构化 AI 核验。模型输出仍由后端校验事实 ID、文章位置、标准值和比较结果。

## 质检结果体验

文章编辑页的 AI 质检卡增加“事实核验”维度，显示：

- 本次策略：原子事实、知识库检索或混合质检。
- 使用的事实库版本。
- 命中、冲突、未覆盖、歧义和回退数量。
- 原子事实 Token、回退 Token 和总耗时。

每条事实问题展示：

| 字段 | 内容 |
|---|---|
| 文章表达 | 命中的原句和位置 |
| 标准答案 | 当前活动事实值 |
| 判断 | 支持、冲突、信息不足或已回退 |
| 比较方式 | 数值严格、日期范围、文本语义等 |
| 来源 | 知识库章节和证据摘录 |
| 版本 | 知识库名称与事实库 vN |

高重要度且适用性完整的数字冲突进入硬门禁。歧义、陈旧、跨范围和事实库外内容继续使用现有证据链路，不能直接判通过或阻断。

任务创建和单篇质检不增加新的原子事实开关。系统根据绑定知识库的活动版本自动选择路径，并显示一行只读说明，比如“2 个知识库有可用事实，其余内容继续使用知识库核验”。灰度与冻结继续由现有服务端 rollout 管理。

## 数据与 API 决策

本轮不新增持久化实体。继续使用现有 6 类原子事实数据和 `ArticleAiQualityCheck` 的 JSON 快照字段：

- `execution_meta.atomic_facts` 保存模式、版本、覆盖率、回退原因、算法版本和耗时。
- `issues` 保存可展示的事实冲突与证据引用。
- `usage_meta` 保存原子通道和回退通道的 Token。
- 质检指纹加入活动 revision ID、库哈希、源哈希和服务状态。

实体变化：0 张新表，1 个新的管理端工作台页面，1 个新的管理端 GET 路由。现有写路由继续复用。后续需要跨百万条检查做聚合查询时，再评审是否把 `inspection_mode` 提升为索引列。

## Laravel 与队列边界

- 所有事实、值、证据、运行和版本都通过知识库父关系解析，禁止脱离父资源读取 ID。
- 控制器只负责 Form Request、授权、资源解析、调用用例和选择响应。运行状态映射放到 Presenter 或 Resource。
- 生成协调器负责生命周期编排，候选持久化、冲突解决和状态投影保持单一职责。
- 每个事实库只允许一个活动生成，数据库 `active_key`、事务锁和输入哈希共同保证正确性。
- 进入 `Bus::batch()` 的任务必须使用 `Batchable`。最终化、取消和失败处理均可重复执行，并释放活动键。
- AI 子任务继续使用限流、指数退避、明确超时和 `failed()`。保持 `retry_after > worker timeout > job timeout`。
- 队列只传证据描述符，执行时根据 chunk ID 和哈希读取正文，控制载荷并防止陈旧输入。
- Blade 只渲染已经准备好的视图数据。事实、运行、冲突和修订均分页或设置硬上限，不在 Blade 查询或计算候选哈希。

## 实施顺序

### 迭代 1：让事实库可用、可理解

交付内容：

- 新增独立工作台路由、控制器查询和页面。
- 知识库列表与详情增加状态摘要和入口。
- 建立用户状态投影、准备度检查和动态主操作。
- 重做事实列表、详情面板、审核队列、冲突筛选和发布确认。
- 生成弹窗补齐恢复、取消、真实进度、完成摘要和失败引导。
- 事实、运行、冲突和版本分页，拆分 Blade 组件。
- 补齐中文、英文、葡萄牙语文案。

合并条件：现有事实 API 行为不变，原子事实仍未影响正式质检。

验收：KB23 的 20 条事实可以在工作台完成筛选、逐条审核、证据检查和发布准备度判断。刷新页面可以恢复活动生成。键盘、焦点、320px 至 1440px 布局和减少动态效果设置通过检查。

回滚：移除新入口并恢复详情页摘要，现有写接口和数据保留。

### 迭代 2：补齐比较器并进入影子质检

交付内容：

- 实现主张提取、事实编译、召回、适用性、归一化和比较服务。
- 为数值、日期、百分比、范围、版本、URL、文本和否定引用建立契约测试。
- 质检指纹加入活动事实版本。
- 影子结果写入 `execution_meta.atomic_facts`，不改变分数和发布门禁。
- 采集覆盖率、比较方式、回退原因、Token 和耗时。

合并条件：影子任务失败不影响现有质检，灰度保持 0。

验收：KB23 对照文章中的版本冲突稳定返回 `contradicted`；未提及事实返回 `not_covered`；缺时间或范围的表达返回 `ambiguous`；文章结论保持由当前链路决定。

回滚：停止影子派发，删除影子展示，现有质检继续运行。

### 迭代 3：解释结果并完成上线评测

交付内容：

- 文章质检卡增加事实核验维度和逐条对照。
- 工作台增加覆盖率、冲突率、回退率、Token 和耗时摘要。
- 扩展评测命令，输出决策一致性、严重冲突召回率、安全误审率和置信区间。
- 建立 30 至 50 篇人工标注文章集，覆盖数字、日期、版本、否定引用、历史事实和多知识库冲突。
- 统一原子事实问题与评分器契约，消除“问题发现冲突，结论仍通过”。

合并条件：页面可以展示影子结果，正式门禁仍关闭。

验收门槛：

| 指标 | 门槛 |
|---|---:|
| 严重事实冲突召回率 | ≥ 97% |
| 安全内容误审率 | ≤ 3% |
| 问题与最终决策一致率 | ≥ 95% |
| 已覆盖样本的输入 Token 降幅 | ≥ 35% |
| 原子确定性比较 p95 | < 50ms |
| 影子任务对主质检超时影响 | 0 |

### 迭代 4：混合质检灰度

交付内容：

- `supported` 主张跳过重复知识库核验。
- 适用性完整的 `contradicted` 进入统一评分和门禁。
- 未覆盖、歧义、陈旧和冲突继续逐条回退。
- 复用现有 rollout 与冻结机制，按 0%、10%、25%、50%、100% 推进。
- 健康检查覆盖活动 revision 读取、缓存、回退率、比较异常和决策漂移。

每个灰度阶段至少观察一个完整业务周期。任何阶段触发严重冲突漏检、误阻断超过 3%、回退率异常或延迟回归，立即冻结原子事实通道，恢复知识库质检。

合并条件：灰度为 0 时输出与当前正式链路一致。

回滚：设置原子事实灰度为 0 或冻结通道，无需回滚事实库和发布版本。

## 风险与处理

| 风险 | 处理方式 |
|---|---|
| AI 生成候选质量不稳 | 候选只进入工作区，证据和审核通过后才能发布 |
| 事实版本与知识源漂移 | 发布指纹、chunk 哈希、证据重连和 `stale` 回退 |
| 数字相同但口径不同 | 适用性先检查时间、范围、单位、币种和运算符 |
| 多知识库给出冲突值 | 标记 `conflict` 并回退现有质检，不按绑定顺序裁决真值 |
| 页面在 200 条事实后变慢 | 独立页面、分页、限列、预加载和按需加载详情 |
| 影子任务增加队列压力 | 独立队列预算、去重、最大年龄和失败不影响主链路 |
| 正式门禁发生误阻断 | 人工标注集、分阶段灰度、独立冻结和逐条回退 |

## 审批点

请确认以下五项决策：

1. 接受独立“原子事实工作台”，知识库详情只保留摘要和入口。
2. 接受四段实施顺序：工作台、影子比较、结果解释与评测、混合灰度。
3. 任务和单篇质检采用自动路由，不增加用户开关。
4. 首轮复用现有数据表和质检 JSON 字段，不新增持久化实体。
5. 文章生成事实约束延后到混合质检稳定之后。
