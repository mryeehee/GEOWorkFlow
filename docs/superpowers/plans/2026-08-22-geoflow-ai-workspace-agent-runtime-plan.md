# GEOWorkFlow AI 工作台 Agent 中间层与 GEOHub Skill 升级方案

> 状态：最终评审版，待确认实施
> 日期：2026-08-22
> 版本：Final v1.0
> 实施目标：`codex/admin-ui-v3` 工作树
> 页面：`/admin/ai-workspace`

## 方案结论

推荐在现有 Laravel 单体应用内建设一套模块化 Agent 中间层，让 AI 工作台成为 GEOWorkFlow 的对话式操作入口。

用户面对一个统一的 `GEOHub` 超级 Skill。系统内部由能力目录、意图识别、计划编译、工作流执行、审批审计和结果呈现共同支撑。模型负责理解、生成计划草案和组织语言，PHP 代码负责权限、计划校验、审批、幂等、状态迁移和业务写入。模型无法匹配系统能力时，工作台进入普通问答模式，并明确标记“本次仅提供建议，未执行系统操作”。

首版保持 Laravel 单体部署。现有业务服务、后台权限、PostgreSQL、Redis、队列、Reverb 和 Laravel AI SDK 都可以直接复用，部署和回滚也更简单。未来如果 Agent 执行量增长，可以沿着队列接口把工作流执行器拆成独立服务，前端协议和能力定义无需重做。

## 最终评审修订

本轮评审发现并修正了十一项会影响实施安全或范围判断的问题：

1. 全后台能力登记原计划放在最后阶段，无法支撑首版完整意图识别。最终版增加阶段零，先完成能力盘点、分级和评测基线。
2. 模型生成计划后缺少确定性校验。最终版增加 `AiPlanCompiler` 与 `AiPlanValidator`，任何系统操作都必须先编译成受控步骤。
3. 模型自报置信度不适合直接决定执行。最终版改为组合置信度，并把必填字段、候选冲突、权限和风险校验纳入执行门槛。
4. Laravel AI 原生审批状态与业务审批表可能形成双重事实来源。最终版明确由 `AiWorkflowEngine` 和 GEOWorkFlow 业务表管理执行与审批，SDK 会话表只保存对话。
5. 原计划的幂等键无法单独覆盖“业务动作成功、步骤状态写入失败”的窗口。最终版加入步骤租约、事务内执行记录、领域幂等键和外部结果对账。
6. 审批缺少防篡改、过期和对象变化检查。最终版增加计划摘要、参数摘要、对象版本、审批有效期和执行前复检。
7. 取消、外部超时和模型故障切换的边界不够清楚。最终版增加 `cancel_requested`、`outcome_unknown`，并规定写入开始后锁定模型与计划版本。
8. 90 天保留策略缺少自动清理。最终版增加定时清理任务，保留脱敏审计摘要，按期删除完整会话载荷。
9. 路由数量只能用于覆盖审计，不能直接代表可执行能力。最终版把路由、服务和页面归并为业务能力，并为每条能力设置成熟度状态。
10. 原目录草案新增了项目中尚未使用的 `app/Domain` 根目录。最终版改为扩展现有 `app/Ai`、`app/Contracts`、`app/Services` 和 `app/Console` 结构。
11. 对话 Agent 直接调用读取工具会形成第二条执行路径。最终版要求所有系统读取和写入都先编译为计划，再由工作流引擎执行。

## 当前系统已经具备哪些条件

本方案以 2026-08-22 的运行页面、当前工作树代码和实际路由为依据。

### AI 工作台仍是演示交互

当前页面已经具备清楚的起始态、对话态、进度态和结果确认态，视觉方向也已经与 Admin UI V3 公共壳层统一。实际交互仍由前端定时器模拟：

- `AiWorkspaceController` 只返回 Blade 视图。
- `resources/js/admin/ai-workspace.js` 在浏览器中依次切换六个演示步骤。
- 页面没有保存会话、识别意图、追问缺失字段、调用工具或创建真实任务。
- “一键确认并创建任务”只改变按钮状态，不会写入数据库。
- 结果中的页数、任务数和站点数都是固定演示文案。

### 后台功能足够支撑第一批高频工作流

当前运行实例共有 258 条后台路由，其中 99 条包含 GET 或 HEAD，159 条会改变状态。现有能力已经覆盖：

| 领域 | 已有能力 |
|---|---|
| 数据与分析 | 运营总览、内容分析、流量分析、线索分析、分发分析、AI 可见性分析 |
| 任务 | 创建、更新、启停、立即执行、健康检查、运行监控、队列与实时刷新 |
| 内容 | 创建草稿、编辑、AI 生成、风险扫描、审核、状态管理、回收站 |
| 内容资产 | 知识库、企业知识、标题库、关键词库、图片库、作者、分类、URL 导入 |
| 分发 | 渠道管理、健康检查、预览、发布、重试、设置同步、托管站点 |
| 网站运营 | 网站与品牌设置、首页模块、主题、表单、线索、访问记录 |
| AI 配置 | 模型、服务商、提示词、专用提示词、连接与结构化输出检测 |
| 系统管理 | 管理员、令牌、安全、审计、系统更新与回滚 |

这些功能分散在 57 个控制器和 136 个服务类中。Agent 层应调用领域服务和专用 Action，路由清单只用于发现与覆盖审计。直接把 258 条路由全部暴露给模型会增加误选、越权和参数错误。

### Laravel AI SDK 可以承担通用 Agent 能力

项目当前安装 `laravel/ai v0.10.3`。本地包代码已包含工具调用、结构化输出、会话记忆、工具审批、流式响应、队列调用、广播、模型故障切换和测试 Fake。现有 `MarkdownContentWriterAgent`、`OpenAiRuntimeProvider`、`AiUsageQuotaService` 和动态模型配置可以继续使用。

项目尚未发布 Laravel AI 的会话表，也没有通用的工具注册、模型能力检查和 Agent 工作流记录。这些属于本次建设范围。

当前代码库中没有发现可直接运行的 GEOHub Agent、超级 Skill 定义或工具注册实现。因此，本方案把 GEOHub 视为待建设的产品能力总入口，并将现有后台服务作为它的首批执行基础。如果另有独立 GEOHub 代码库或接口，实施阶段先完成能力协议对照，再决定复用或适配范围。

## 建设目标与验收口径

### 产品目标

AI 工作台需要完成四类工作：

1. 理解用户想完成的业务目标，并判断 GEOWorkFlow 是否具备对应能力。
2. 信息不足时提出少量、明确的追问，并能利用当前页面、当前账号和前文自动补齐上下文。
3. 把一个自然语言请求拆成可审核、可执行、可取消、可恢复的步骤。
4. 系统能力覆盖不到时给出普通 AI 答复，同时避免产生已经执行过操作的错觉。

### 首版验收指标

| 指标 | 通过标准 |
|---|---:|
| 支持意图 Top-1 准确率 | 在固定评测集上不低于 90% |
| 必填信息缺失识别召回率 | 不低于 95% |
| 受限或未知操作拦截率 | 固定安全评测集上 100% |
| 未授权写入 | 0 |
| 重复提交造成的内部重复业务记录 | 0 |
| 结果未知的外部操作自动重试 | 0 |
| 无权限会话或任务越权读取 | 0 |
| 首个状态反馈 | 95% 请求在 1.5 秒内进入“正在理解”或排队状态 |
| 运行记录可追溯 | 每次工具调用都能查到输入摘要、操作者、结果和审批记录 |
| 状态表达 | 普通问答、系统执行、失败、部分完成、取消和结果未知可明确区分 |

### 本次范围

- 会话与上下文管理。
- 意图识别、缺失字段提取、追问和普通问答降级。
- GEOHub 能力注册表与领域工具协议。
- 真实的读取、草稿创建、任务编排、分发预览与经审批的执行。
- 多步任务状态、队列、实时事件、取消、重试和结果链接。
- 管理员权限、审批、幂等、额度、审计和数据保留。
- AI 工作台页面的完整交互升级。
- 中文、英文、日文、西班牙文、俄文和葡萄牙文界面文案。

### 暂不开放的能力

- 任意 SQL、Shell、文件系统或后台路由调用。
- 自动修改管理员、API Token、模型密钥和安全设置。
- 自动执行系统升级、回滚、数据清空和永久删除。
- 绕过文章审核、风险扫描、渠道删除双重确认或现有权限中间件。
- 依赖浏览器自动化的第三方平台发布。
- 由模型动态生成 PHP 工具并立即运行。
- 在对话框直接上传新附件。首版从现有素材库、知识库或 URL 导入中选择来源。
- 首版对外提供 MCP Server。

这些模块可以被意图识别和普通问答理解，系统只返回说明、影响范围和对应后台入口。

## 运行架构

```text
管理员
  │
  ▼
AI 工作台 HTTP 接口
  │  鉴权、CSRF、限流、会话归属检查
  ▼
AiWorkspaceOrchestrator
  ├── AiContextResolver
  │     ├── 当前管理员与权限
  │     ├── 当前站点与会话选择
  │     └── 可见业务对象的最小数据投影
  │
  ├── IntentResolverAgent
  │     ├── 意图分类
  │     ├── 槽位提取
  │     └── 追问或执行模式判断
  │
  ├── AiCapabilityRegistry
  │     ├── GEOWorkFlow 系统能力
  │     ├── GEOHub 复合工作流
  │     └── 权限、风险和输入定义
  │
  ├── GeoHubAgent
  │     ├── 普通问答
  │     ├── 计划草案
  │     └── 结果解释
  │
  ├── AiPlanCompiler / AiPlanValidator
  │     ├── 能力与参数校验
  │     ├── 权限、风险与依赖校验
  │     └── 生成不可变的版本化执行计划
  │
  └── AiWorkflowEngine（执行与审批唯一事实来源）
        ├── 审批与幂等
        ├── 队列和重试
        ├── 领域工具适配器
        │     └── 现有 GEOWorkFlow Services / Actions
        └── Reverb 进度事件

PostgreSQL
  ├── Laravel AI 会话与消息
  └── Run、Step、Approval、Artifact
```

`AiWorkspaceOrchestrator` 是稳定的应用入口。所有读取和写入都先生成 `AiWorkflowPlanDraft`，再由 `AiPlanCompiler` 编译成版本化的 `AiWorkflowPlan`。计划中的能力 key、参数、依赖、风险、审批策略和对象范围全部来自能力注册表。编译失败时进入追问、普通问答或受限说明，不进入执行队列。

`AiWorkflowEngine` 是执行状态和审批状态的唯一事实来源。Laravel AI 会话表负责保存对话和模型消息，首版不使用 SDK 消息中的审批状态控制业务写入，避免两套状态互相覆盖。

## GEOHub 超级 Skill 如何组成

产品内的 Skill 采用统一定义：一条能力包含语义说明、输入字段、权限、风险、工具实现和结果展示。它与 Codex 的 `SKILL.md` 文件没有运行时依赖。

### 用户只看到 GEOHub

`GeoHubAgent` 是工作台的统一身份，负责维持对话、生成和解释计划草案、汇总结果并处理普通问答。所有系统读取、状态变更和外部操作都由 `AiPlanCompiler` 与 `AiWorkflowEngine` 接管，模型不直接调用领域工具。

GEOHub 的系统提示保持短小，只放长期稳定的身份、授权边界、结果表达和审批规则。业务知识进入能力注册表，具体参数进入能力的输入 Schema，避免所有后台功能都堆进一个超长提示词。

### 能力注册表是唯一能力来源

每条能力定义至少包含以下字段：

| 字段 | 用途 |
|---|---|
| `key` | 稳定标识，如 `task.create_draft` |
| `title` | 给用户和审计日志显示的名称 |
| `description` | 适用目标、可完成的结果和能力边界 |
| `examples` | 真实的用户表达样本 |
| `coverage_refs` | 对应的后台路由、页面和领域服务，用于覆盖审计 |
| `input_schema` | 必填、可选、默认值和可从上下文推断的字段 |
| `permission` | 普通管理员、超级管理员或特定策略 |
| `risk_level` | `read`、`draft_write`、`state_change`、`external`、`restricted` |
| `execution_scope` | `local_read`、`remote_read`、`internal_write` 或 `external_write` |
| `cost_class` | 免费、低成本、模型计费或外部配额，用于预算和限流 |
| `data_classification` | `public`、`internal`、`confidential` 或 `personal`，决定可传入模型的字段 |
| `approval_policy` | 自动、计划确认、逐步确认或禁用 |
| `maturity` | `advisory`、`read_ready`、`draft_ready`、`execute_ready`、`restricted` |
| `version` | 能力定义版本，用于计划、审批和回放 |
| `tool` | 对应的领域工具类，未开放执行时可以为空 |
| `result_presenter` | 结果摘要、业务对象链接和下一步建议 |
| `feature_flag` | 能力是否已经开放 |
| `eval_cases` | 正例、近似意图、缺参和拒绝样本 |

注册表采用 PHP 类型对象管理，启动时校验 key 唯一、版本有效、权限存在、路由名有效，并按成熟度检查工具是否存在。阶段零提供只读的注册表审计命令，将路由、控制器、领域服务和页面归并到业务能力。每条后台路由必须出现在某项能力的 `coverage_refs` 或显式排除清单中，架构测试持续检查新增路由。该命令不会自动把后台路由变成工具。

首版开始前完成全后台能力登记。尚未完成领域适配和安全测试的能力标记为 `advisory`，GEOHub 可以解释能力和提供后台入口。通过对应门禁后，成熟度再提升到读取、草稿或执行级别。

### 能力定义按意图动态筛选

每次请求只向 `GeoHubAgent` 提供当前意图需要的 3 到 10 条能力定义与计划模板。领域工具只注册到 `AiWorkflowEngine`，读取也生成单步计划，避免对话 Agent 和工作流引擎形成两条执行路径。模型原生工具调用可以作为后续优化，首版运行不依赖供应商的工具调用协议。

## 意图 Skill 与追问机制

### `IntentResolverAgent` 的输出

意图识别使用 Laravel AI 的结构化输出，固定返回以下信息：

| 字段 | 说明 |
|---|---|
| `request_type` | `system_query`、`system_action`、`general_answer`、`unsupported` |
| `primary_intent` | 主意图 key |
| `secondary_intents` | 复合请求中的后续意图 |
| `capability_keys` | 注册表候选能力 |
| `goal_summary` | 对用户目标的短句归纳 |
| `provided_slots` | 用户明确给出的字段 |
| `inferred_slots` | 从会话、账号、当前页面和系统默认值推断的字段 |
| `missing_required_slots` | 无法执行时仍缺少的必填字段 |
| `model_confidence` | 0 到 1 的模型判断信号，只用于组合评分 |
| `risk_level` | 本次请求预估的最高风险 |
| `next_mode` | `clarify`、`plan`、`answer` 或 `reject` |
| `clarification_questions` | 最多三个问题，按信息增益排序 |

后端会校验结构化结果。能力 key、权限、输入类型和风险等级以注册表为准，模型输出不能提升权限或降低风险。

后端计算最终 `resolution_score`，输入包括模型判断信号、能力样本匹配、必填字段完整度、候选能力差距、当前权限和评测校准结果。模型自报的分数不会单独触发执行。两个候选能力接近、存在对象歧义或能力版本不匹配时，系统直接降低分数并追问。

### 什么时候追问

| 条件 | 系统行为 |
|---|---|
| `resolution_score` 不低于 0.85，必填字段齐全 | 读取类任务可进入单步计划，写入类任务生成可审核计划 |
| `resolution_score` 在 0.60 到 0.84 | 展示当前理解，询问一个最能排除歧义的问题 |
| `resolution_score` 低于 0.60 | 给出两个最可能的目标供用户选择，并保留自由输入 |
| 存在缺失的必填字段 | 一次询问最多三个字段，优先用选择项和系统已有对象 |
| 多个意图存在执行顺序冲突 | 先确认最终目标和停止条件 |
| 请求超出能力范围但模型可以回答 | 进入普通问答，显示“未执行系统操作” |
| 请求涉及受限操作 | 说明限制、影响范围和后台入口，不生成可执行步骤 |

追问应尽量复用已有信息。当前站点、当前管理员、会话最近选择的知识库、默认时间范围和可用渠道都由 `ContextResolver` 提供。可从系统唯一确定的字段直接补齐，并在计划里显示推断依据。用户已经给出的字段不会重复询问。

### 执行计划必须通过编译

`GeoHubAgent` 只生成 `AiWorkflowPlanDraft`。`AiPlanCompiler` 按能力注册表生成不可变的 `AiWorkflowPlan`，每个步骤至少包含：

| 字段 | 用途 |
|---|---|
| `plan_version` | 计划格式版本 |
| `capability_key` 与 `capability_version` | 锁定能力语义和实现版本 |
| `depends_on` | 步骤依赖，依赖图必须无环 |
| `resolved_input` | 经过类型校验和权限裁剪的参数 |
| `input_sources` | 参数来自用户、上下文、默认值或前序步骤 |
| `target_fingerprint` | 目标对象及关键版本的摘要 |
| `risk_level` 与 `approval_policy` | 从注册表重新计算 |
| `idempotency_key` | 传入领域动作和外部适配器 |
| `expected_effects` | 预计创建、修改或发送的对象 |
| `timeout` 与 `retry_policy` | 按能力定义的执行约束 |
| `result_contract` | 结果结构、Artifact 和用户可见状态 |

`AiPlanValidator` 拒绝未知能力、循环依赖、越权对象、超出步骤上限、参数来源不明、风险降级和未开放能力。计划确认后冻结版本；用户修改参数、对象变化、能力版本变化或审批过期都会生成新版本并重新确认。

### 普通问答降级

`general_answer` 模式保留 GEOHub 的对话身份，可以回答 GEO、内容、产品操作和通用知识问题。该模式不读取当前管理员的业务数据和企业知识；需要检索企业知识时，系统切换到 `system_query`，生成读取计划并标记数据来源。普通问答遵守三条规则：

- 回复顶部标记“建议答复”。
- 回复底部标记“本次未执行系统操作”。
- 不生成虚构的任务编号、文章链接、分发结果和系统数据。

涉及 GEOWorkFlow 页面、权限和操作入口的问题优先使用能力注册表中的 `system.guide`，只返回已登记的命名路由。注册表没有对应事实时，回复明确说明当前无法确认，不猜测菜单名称或页面路径。

涉及实时外部信息时，首版说明知识时效。联网搜索只在模型供应商已经支持、管理员显式开启且安全策略允许时加入，首版没有新的搜索服务依赖。

## 能力分级与首版开放范围

### 风险分级

| 等级 | 示例 | 默认处理 |
|---|---|---|
| `read` | 查询分析、搜索资产、检查渠道健康 | 权限通过后执行；远程读取额外受限流和预算约束 |
| `draft_write` | 创建任务草稿、文章草稿、知识草稿 | 展示计划，一次确认 |
| `state_change` | 启停任务、改变审核状态、提交 URL 导入 | 逐步确认，记录原值和新值 |
| `external` | 分发文章、同步站点设置、发布主题 | 预览影响，逐步确认 |
| `restricted` | 永久删除、密钥、安全设置、系统更新 | Agent 禁用，只提供入口和说明 |

当前原型中的“低风险步骤自动确认”在首版隐藏。读取动作默认直接执行，草稿和业务状态变更按上表审批，外部动作保留现有预览与确认流程。

每次审批绑定管理员、Run、Step、计划版本、能力版本、最终参数摘要和目标对象摘要，默认 30 分钟失效。执行前重新检查权限、对象版本、业务状态和影响范围。任何摘要变化都会让原审批失效。用户在审批卡修改参数时，接口只生成新计划版本并返回新的确认内容，不会在同一次请求中执行。审批接口使用数据库条件更新保证一次生效，重复点击返回原决定。

同一能力、同一内容和同一风险等级的批量外部操作可以合并为一次审批，审批卡必须展示完整目标矩阵。执行时仍按目标拆成独立 Step，逐项记录成功、失败和结果未知；目标列表变化会让整批审批失效。

## 第一批高频对话式任务

### AI 可见性下降诊断

用户示例：分析近 30 天 ChatGPT、豆包和 DeepSeek 的品牌可见性，找出引用下降内容并生成优化任务。

必填信息包括时间范围、目标来源和任务产出。系统可从站点默认值补齐品牌与站点。流程依次读取可见性数据、定位下降页面、匹配知识和关键词、生成任务草稿、展示任务参数。创建草稿需要一次确认，启动任务另行确认。

### 从主题创建内容任务

用户示例：围绕“企业 GEO 评估”创建每周两篇的内容任务，使用产品知识库，先审核再发布。

必填信息包括主题或标题来源、知识库、AI 模型、生成数量、频率和审核策略。缺少唯一值时，追问卡直接列出当前可用对象。结果包含任务草稿、预计首次运行时间和编辑入口。

### 诊断并优化存量内容

用户示例：找出近 60 天访问下降且 AI 引用减少的文章，给出修改建议并建立待审核草稿。

流程读取流量、内容和 AI 可见性信号，筛选文章，生成逐篇原因与修改建议。首版只创建修订草稿，不覆盖原文。每篇草稿链接回内容编辑页，批量更新状态需要确认。

### 建设企业知识项目

用户示例：把产品资料和官网内容整理成企业知识项目，生成一版可审核的知识草稿。

流程建立项目草稿、读取用户选择的来源、生成内容、执行校验并保存修订。发布知识项目需要独立确认。资料不足时，追问需要的来源类型和目标受众。

### URL 导入与知识同步

用户示例：导入这批官网链接，提取正文后放进产品知识库。

系统先生成 URL 清单与目标知识库预览，再执行抓取和解析。网络请求沿用现有出站安全策略。导入和提交分为两次状态变更，失败 URL 可以单独重试。

### 多站分发

用户示例：把本周审核通过的内容同步到三个 GEOWorkFlow Agent 站点。

流程读取审核通过内容、候选渠道和渠道能力，展示内容与目标站点矩阵，执行现有分发预览。用户确认后才入队。结果显示每个站点的成功、失败、重试和远程内容链接。

### 日报与周报

用户示例：总结今天内容生产、AI 可见性和分发情况，列出明天优先处理的三件事。

这是读取类复合工作流，可以直接执行。输出中的每个数字都带数据来源链接，建议项不自动转成任务。用户点击“创建为任务”后进入草稿确认。

### 线索与内容机会分析

用户示例：分析最近一个月的线索来源和高频问题，给出内容选题。

流程读取线索统计、访问来源和现有关键词，输出主题、依据和建议优先级。创建标题库或任务属于后续草稿写入，需要确认。

## 工具和现有后台如何连接

### 领域工具只调用稳定业务入口

每个工具完成一个清楚的业务动作。读取工具可以调用查询服务，写入工具调用现有领域服务或新增的单用途 Action。工具不调用 Blade 控制器，也不模拟后台表单请求。

这些工具实现 GEOWorkFlow 内部的 `AiWorkspaceTool` 契约，由 `AiWorkflowEngine` 按已编译步骤解析和调用。`GeoHubAgent::tools()` 首版保持为空，避免供应商工具协议绕过计划编译器。

第一批工具按目录组织：

```text
app/Ai/Tools/Analytics/
app/Ai/Tools/Visibility/
app/Ai/Tools/Tasks/
app/Ai/Tools/Articles/
app/Ai/Tools/Knowledge/
app/Ai/Tools/Distribution/
app/Ai/Tools/Site/
```

工具统一返回：成功状态、用户可读摘要、结构化数据、业务对象链接、警告、可重试错误码和后续建议。日志保存参数摘要，API Key、渠道密钥、文章敏感内容和个人线索信息会被清理。

### 控制器中的业务逻辑需要逐步下沉

现有任务 API 已经有 `TaskLifecycleService`，分发、URL 导入、知识检索和内容生成也有可复用服务。部分后台写入仍集中在控制器中。对应工具实施时先提取单用途 Action，并让原控制器和 Agent 工具共同调用，避免两套业务规则。

### 模型能力需要检测

工作台首版依赖结构化输出、流式文本和会话。`ai_models` 增加 `capabilities_json` 与 `capabilities_checked_at`，AI 配置页扩展“检测工作台能力”。检测结果至少覆盖：普通文本、流式输出、结构化输出，并记录工具调用和工具审批是否可用，后两项不作为首版执行前提。

`AiWorkspaceModelResolver` 按启用状态、模型类型、能力检测、调用额度和 `failover_priority` 选择模型。可用模型只支持普通文本时，工作台保留问答和人工追问，系统执行入口显示配置提示。

每个 Run 记录意图模型、计划模型、供应商和能力检测版本。读取与计划阶段允许故障切换，切换后重新生成并校验计划草案。第一个写入步骤开始后，已确认计划保持冻结，模型故障只影响后续文本整理，不会触发自动重规划或更换业务动作。需要新模型继续规划时，系统创建新的计划版本并重新审批。

## 工作流状态、审批和数据模型

### 状态机

```text
received
  ├── clarifying ──────────────── received
  ├── answering ───────────────── completed
  └── planning ── validating_plan
                      ├── awaiting_approval ── queued
                      ├── queued
                      └── rejected

queued ── running
            ├── awaiting_step_approval ── queued
            ├── cancel_requested ── cancelled / completed / outcome_unknown
            ├── partially_completed
            ├── outcome_unknown
            ├── failed
            └── completed
```

状态迁移由 `AiWorkflowEngine` 控制。客户端事件只更新展示，无法直接改写运行状态。

### 数据表

发布 Laravel AI 的会话迁移，增加 `agent_conversations` 和 `agent_conversation_messages`。GEOWorkFlow 再增加四张业务表：

| 表 | 关键字段与用途 |
|---|---|
| `ai_workspace_runs` | UUID、会话、管理员、意图、组合评分、状态、最高风险、模型信息、计划版本、上下文摘要、幂等键、错误和时间 |
| `ai_workspace_steps` | Run、顺序、能力与版本、输入、目标摘要、状态、风险、审批 ID、幂等键、租约、尝试次数、结果和错误 |
| `ai_workspace_approvals` | Run、计划与能力版本、参数摘要、目标矩阵摘要、决定、理由、决定人、过期时间和决定时间，可被多个同质 Step 引用 |
| `ai_workspace_artifacts` | Run、Step、对象类型、对象 ID、标题、路由名和安全元数据 |

`Admin` 关联 Laravel AI 会话。继续会话前，控制器显式校验会话属于当前管理员，Laravel AI SDK 本身不会替应用完成这一层授权。

迁移为管理员、会话、Run 状态和更新时间建立组合索引。管理员与请求幂等键、Run 与步骤顺序、步骤幂等键、Run 与审批摘要分别建立唯一约束。Artifact 只保存命名路由和对象标识，返回页面时重新授权并生成 URL，不长期保存带权限参数的链接。

计划和结果中的敏感值只保存摘要。完整会话与运行载荷默认保留 90 天。定时清理任务删除到期会话与消息，清空 Run 和 Step 中的计划、输入、结果与上下文载荷，保留 Run 标识、能力 key、状态、操作者和时间等脱敏审计字段。Run 的会话关联允许置空，脱敏动作摘要继续按现有管理员活动日志策略保存。用户可以提前归档会话，永久清理由保留任务统一执行。

### 幂等与并发

- 每条消息生成请求幂等键，重复提交返回已有 Run。
- 每个写入 Step 持有独立幂等键和短租约。内部领域动作在同一数据库事务中记录执行凭据，并把幂等键传到目标记录或专用执行账本。
- 外部适配器优先使用渠道提供的幂等键。渠道缺少该能力时，发送前保存请求指纹，超时后先按远程 ID 或内容指纹对账。无法确认结果时进入 `outcome_unknown`，停止自动重试并等待人工处理。
- 每个管理员最多同时运行两个工作流，第三个进入队列。
- 每个 Run 最多 20 个步骤和 8 次模型调用，结构化输出校验失败最多自动重试一次。
- 同一业务对象的写操作使用数据库锁或现有租约服务。
- 渠道删除、同步和发布继续使用现有预览、指纹和操作租约。
- 调度器定期扫描长时间停留在 `queued` 的 Run 和过期步骤租约。恢复前重新检查幂等凭据与领域结果，确认未执行后才重新入队。

系统不提供通用事务回滚。每条可逆能力可以登记补偿动作，补偿也需要权限和审批；内容已发布、消息已发送等不可逆结果进入部分完成或人工处理。取消采用协作式语义：尚未开始的步骤立即取消，正在进行的外部请求先进入 `cancel_requested`，收到明确结果后再落为取消、完成或结果未知。

## HTTP、实时事件和页面交互

### 后台接口

沿用现有后台前缀、管理员认证、语言、活动日志和 UI V3 中间件。新增路由：

| 方法与路径 | 用途 |
|---|---|
| `GET /admin/ai-workspace` | 工作台页面与最近会话 |
| `POST /admin/ai-workspace/conversations` | 新建会话 |
| `GET /admin/ai-workspace/conversations` | 分页读取当前管理员的会话 |
| `GET /admin/ai-workspace/conversations/{conversation}` | 读取消息、Run 和结果 |
| `POST /admin/ai-workspace/conversations/{conversation}/messages` | 发送用户消息并创建 Run |
| `GET /admin/ai-workspace/runs/{run}` | 获取权威状态快照，用于刷新和轮询恢复 |

### 页面保留当前视觉方向

视觉主题继续采用浅色、精确、克制的运营控制台。现有蓝灰色变量、公共侧栏、顶部栏、最大内容宽度和圆角体系继续使用，CSS 维持 Tailwind v4 入口与 `app.css` 中的 `gf-*` 组件层，不引入新的 CSS Modules 或 CSS-in-JS。

**视觉主张**：让真实状态、数据依据和待确认动作成为页面最醒目的内容，装饰保持安静。
**内容顺序**：说明当前上下文，理解用户目标，必要时追问，展示计划，执行并汇总结果。
**交互主张**：键盘发送不加动画；偶发的计划出现、审批和完成状态使用 160 到 240 毫秒的透明度与位移动画，并遵守 `prefers-reduced-motion`。

### 页面需要补齐的状态

| 状态 | 界面内容 |
|---|---|
| 起始态 | 保留当前标题、输入框和高频任务入口，示例改为真实模板 |
| 正在理解 | 显示真实 Run 状态，超过 1.5 秒才出现持续等待文案 |
| 追问态 | 在对话流中展示问题、候选对象、已推断信息和自由输入 |
| 计划态 | 展示目标、步骤、使用的能力、将读取的数据、将改变的对象和审批边界 |
| 执行态 | 展示真实步骤、时间、状态、警告、取消和重试，不显示模型思维过程 |
| 审批态 | 展示动作、目标、参数、影响、可编辑字段和批准、拒绝按钮 |
| 结果态 | 展示成功、部分成功、失败、已拒绝、已取消、结果未知、业务对象链接和下一步 |
| 普通问答 | 标记“建议答复”和“未执行系统操作” |
| 降级态 | 展示模型、队列、工具或权限问题，提供重试、配置或后台入口 |

对话模式下输入框固定在内容区底部。历史会话在桌面端使用可收起的工作区内侧栏，移动端使用抽屉。审批、追问和结果都在对话流内展开，普通信息溢出不使用模态框。

## 权限、安全和运行约束

### 每次工具调用重新授权

意图识别结果只能筛选候选能力。工具执行前仍要检查当前管理员、目标对象、超级管理员要求、功能开关和业务状态。计划创建后权限发生变化时，执行会停止并返回权限错误。

### 输入和外部内容隔离

- 用户消息、系统读取的资料、网页正文和远程站点响应都按数据处理，不能修改 Agent 的系统约束。
- 上下文中的每段数据记录来源类型、对象 ID 和可信级别。检索内容、网页文本和工具结果不能声明新能力、改写审批策略或触发工具。
- 工具采用允许列表和严格输入 Schema。
- `AiContextResolver` 只传递完成当前任务需要的字段，列表数据先分页、聚合和脱敏，线索内容默认不进入普通问答上下文。
- URL 导入、主题复制和分发继续使用现有出站请求安全策略。
- 日志不记录 API Key、密钥明文、Token、密码和线索个人信息。
- 普通问答不进入工作流执行器。
- 用户输入、模型输出和工具结果分别保存，任何模型生成内容进入 HTML 前都经过转义和现有富文本清理。

### 失败和降级

- 模型不可用时，Run 进入可重试失败状态，已完成的业务步骤不会重复执行。
- Redis 或 Reverb 短时不可用时，页面通过轮询恢复，业务写入按现有队列策略处理。
- Run 已写入而队列派发失败时保持 `queued`，调度器在 Redis 恢复后补派发，幂等键阻止重复入队造成重复业务动作。
- 外部渠道失败时，结果按站点展示成功与失败，不把部分完成显示成全部完成。
- 结构化输出校验失败时，系统只重试一次；第二次失败进入追问或普通问答。
- 能力注册表没有匹配时，系统进入普通问答或受限说明。
- 外部请求超时且无法判断远程结果时进入 `outcome_unknown`，页面提供对账入口，不提供自动重试按钮。

## 分阶段实施

### 阶段零：能力盘点与协议冻结

预计 3 到 5 个开发日。

交付内容包括全后台能力矩阵、业务能力归并、风险与成熟度分级、首批八条工作流输入清单、能力注册表骨架、意图评测基线和 GEOHub 外部接口对照。258 条后台路由全部有归属或明确排除原因，`advisory` 能力也能提供系统说明和后台入口。

阶段门禁：能力 key、版本规则、输入 Schema、权限、风险、数据分类和审批策略通过人工评审，首批执行能力不再依赖路由猜测。如果发现独立 GEOHub 代码库或接口，本阶段完成复用决定。

### 阶段一：真实会话、意图识别和普通问答

预计 6 到 8 个开发日。

交付内容包括 Laravel AI 会话表、工作台 Run 数据、模型能力检测、`IntentResolverAgent`、`GeoHubAgent`、`AiPlanCompiler`、`AiPlanValidator`、会话接口、追问、普通问答、历史会话、保留任务和真实状态 UI。这个阶段开放普通问答、意图识别与计划预览，不执行领域写入。

完成后，AI 工作台可以持续对话、理解全后台能力、追问缺失信息、展示受控计划、解释系统能力并回答覆盖范围外的问题。

### 阶段二：读取工具和 GEOHub 分析工作流

预计 6 到 9 个开发日。

开放运营分析、AI 可见性、内容搜索、知识检索、任务查询、渠道查询和健康检查。加入动态能力筛选、真实结果链接、引用数据来源、实时事件与评测集。

完成后，日报、周报、可见性诊断、内容机会分析和系统查询可以真实运行。

### 阶段三：草稿写入与一次确认

预计 7 到 10 个开发日。

开放任务草稿、文章草稿、企业知识草稿、标题建议和 URL 导入预览。实现计划确认、防篡改审批、领域幂等、Artifact、审批记录、数据保留和控制器业务逻辑下沉。

完成后，AI 可以把分析结果转成可编辑的业务草稿，原有审核门禁继续生效。

### 阶段四：多步执行与外部操作

预计 8 到 12 个开发日。

开放任务启停、URL 导入运行与提交、分发预览、分发发布、失败重试、站点设置同步和托管站点预检。接入队列、Reverb、逐步审批、协作式取消、部分完成、外部结果对账和恢复。

完成后，原型中的“诊断、创建任务、审核后多站分发”可以作为一条真实工作流运行。

### 阶段五：运营治理和持续评测

预计 3 到 5 个开发日。

交付用量与成功率看板、失败分类、提示词版本、能力版本、能力变更审计和回归评测。新增后台模块只有完成能力登记或明确排除后才能通过架构测试，避免意图目录随功能增长而失真。

每个阶段都可以独立合并和发布。后续阶段停止时，已交付能力仍能正常使用。

## 发布、监控和回滚

### 发布顺序

1. 先发布数据库与后端代码，运行时开关保持关闭。
2. 运行模型能力检测和意图评测。
3. 为指定超级管理员开启阶段一，再扩大到普通管理员。
4. 按能力族逐批开启读取、草稿和外部执行工具。
5. 观察模型失败率、平均追问次数、工具失败率、审批过期率、受限请求拦截率、结果未知数和重复提交拦截数。

### 回滚

- 关闭 `GEOFLOW_AI_WORKSPACE_RUNTIME_ENABLED`，页面回到只读入口，现有后台功能继续运行。工作流引擎在每个新步骤前检查开关并停止后续步骤，已经发出的外部请求仍按实际结果记录。
- 已创建的业务草稿继续保留，并能从原后台页面编辑。
- 未开始的 Run 标记取消，运行中的领域任务先进入 `cancel_requested`，再按各自现有取消语义处理。
- 数据库迁移全部是新增表和新增列，代码回滚时可以保留数据，确认不再需要后再执行迁移回滚。
- 外部发布已经成功的内容不做自动反向删除，结果页保留实际状态与人工处理入口。

### 十倍负载下的处理

外部模型延迟和队列等待会先增加。方案通过每管理员并发上限、全局并发上限、读取与外部操作分队列、Run 步骤上限、有界查询、轻量广播和页面轮询降低影响。能力工具不把整张表或整份文章库塞进模型上下文，分析结果通过摘要和业务对象 ID 传递。全局并发默认值为 10，阶段二压测后按队列 Worker 和模型额度调整。

## 依赖、凭据和成本

首版没有新增 Composer 或 npm 运行依赖，也不需要新增第三方账号。运行条件包括：

- 至少一个通过结构化输出检测的启用聊天模型，流式输出用于改善短问答体验。
- 现有模型 API Key，继续由 `ApiKeyCrypto` 解密并通过运行时 Provider 注册。
- PostgreSQL、Redis 和队列 Worker。Reverb 用于实时体验，关闭时回退到轮询。
- 当前管理员权限和已有渠道凭据。

所有 Agent 调用继续使用 `AiUsageQuotaService` 预占和结算每日额度。每个 Run 在开始时计算最大模型轮次、Token 和步骤预算，接近预算时停止扩展计划并请求用户缩小范围。意图识别使用低温度和较小输出上限，普通问答与计划生成按需要使用更高输出上限。每个 Run 记录模型、调用次数、耗时、用量和失败类型，不保存密钥。

## 备选路径与最小版本

### 推荐路径

采用应用内 Agent 中间层、能力注册表、计划编译器和工作流引擎。按一名熟悉现有系统的高级工程师全职投入估算，总投入 33 到 49 个开发日。估算包含开发、自动化测试和阶段验收，不包含外部 GEOHub 接口改造、模型供应商兼容问题和生产数据修复。

### 最小版本

交付阶段零、阶段一、阶段二和 `task.create_draft`，预计 17 到 24 个开发日。它可以完成全系统能力理解、对话、追问、分析、普通问答和任务草稿，暂时不支持文章与知识写入、URL 导入运行和多站分发。这是需要更快上线时的可选范围。

### 暂缓独立 Agent 微服务

独立服务需要重新处理管理员身份、权限、数据库事务、幂等、密钥访问、部署、监控和版本兼容，预计增加 30% 到 50% 的初期工作量。当前规模和现有 Laravel 服务更适合先在单体内建立清楚的接口。队列 Job 和能力工具协议会保留未来拆分条件。

## 关键假设与需要确认的决定

这份方案依赖一个关键假设：现有启用聊天模型中，至少有一个能稳定完成结构化输出。该假设不成立时，阶段一仍可交付普通问答和基于固定选项的追问，计划生成与系统执行保持关闭，直到模型能力检测通过。供应商工具调用能力不影响首版执行链路。

请确认以下默认决定，确认整份方案即表示接受这些默认值：

| 决定 | 推荐默认值 |
|---|---|
| 命名 | 页面模块为“AI 工作台”，助手显示为 `GEOHub`，内部类名为 `GeoHubAgent` |
| 首批执行能力 | 读取分析、任务草稿、文章草稿、知识草稿、URL 导入预览、分发预览 |
| 审批策略 | 读取自动，草稿一次确认，状态变更逐步确认，同质外部操作可按目标矩阵批量确认，受限操作禁用 |

| 首版范围 | 推荐完整六阶段；需要快速上线时采用最小版本 |
