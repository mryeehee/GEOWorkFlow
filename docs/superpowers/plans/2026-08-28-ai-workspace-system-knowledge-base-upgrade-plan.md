# GEOWorkFlow AI 工作台系统知识库与图文回答升级方案

> 状态：最终评审版，待确认实施
> 版本：Final v2.0
> 日期：2026-08-28
> 目标页面：`/admin/ai-workspace`
> 关联页面：`/admin/knowledge-bases`
> 实施顺序：Phase 1 文本知识与站内导航；Phase 2 截图库与图文回答

## 1. 方案结论

推荐把 AI 工作台当前的 PHP 内置帮助目录升级为一套“系统知识库 + 可信站内导航 + 结构化媒体”的帮助体系。

Phase 1 新建一份专用于 AI 工作台的系统知识库，后台名称为「GEOWorkFlow 后台功能与操作指南（AI 工作台专用）」。官方基线以一个 Markdown 文件和一份机器可读清单随代码发布。正文至少包含 10,000 个有效中文汉字，目标内容量为 20,000 至 30,000 个可见字符。系统通过显式、幂等的同步命令写入现有知识库，完成结构化切片和检索。独立的系统知识绑定表提供稳定键和数据库外键删除保护。授权管理员可以二次编辑，保存前完成路由指令校验，保存后记录修订并重建检索索引。编辑页和详情页持续提示：本知识库直接影响 AI 工作台回答。

AI 工作台收到问题后，只检索这份系统知识库，选取相关章节交给模型组织答案。当前界面语言、最近一轮用户问题和上一轮知识来源用于理解追问，历史助手回答不作为事实来源。模型负责语言表达，站内入口由服务端根据命名路由、当前后台前缀和管理员权限生成。回答按问题复杂度扩展前置条件、操作步骤、结果说明、常见问题和相关功能，同时保留现有 SSE 流式输出、会话历史、模型故障转移和安全净化。

Phase 2 建设专用截图素材层。截图与知识章节建立稳定关联，文件放在私有存储中，通过登录鉴权后的站内接口读取。媒体文件按内容哈希形成不可变版本，历史消息固定引用当时版本。服务端根据本轮命中的知识章节选择 0 至 3 张强相关截图，前端使用结构化字段渲染。模型输出中的原始图片地址和链接继续保持不可点击、不可直接渲染，避免权限绕过、外链注入和错误配图。

两个阶段均可独立合并。Phase 1 上线后已经具备完整的文字问答和站内导航能力；Phase 2 延后或取消时，Phase 1 仍可长期运行。

本轮最终评审补齐了数据库级删除保护、显式安装与升级流程、管理员编辑修订、跨语言回答、追问检索、上下文预算、索引版本一致性、媒体版本一致性、图库维护、可观测性和生产回滚边界。方案内已没有依赖实施人员临时决定的关键产品分支。

## 2. 当前状态与证据

### 2.1 当前 AI 工作台链路

当前 `/admin/ai-workspace` 已经具备稳定的产品外壳：

- 管理员鉴权、会话创建、重命名、归档与历史分页。
- SSE 流式状态、正文分片、停止生成、断线和错误处理。
- 已启用对话模型的就绪检测、超时、额度、故障转移和普通文本降级。
- Markdown 表格、列表、引用、代码块和复制能力。
- 服务端生成的相关功能卡片，最多展示 3 个可信站内入口。
- 会话消息持久化，并在 `meta` 中保存相关功能、推荐问题和生成性能。

当前请求链路为：

```text
用户问题
  -> AdminHelpKnowledgeCatalog 本地匹配
  -> 最多 5 条简短帮助事实
  -> AdminHelpAssistant 一次模型调用
  -> SSE 流式正文
  -> 服务端追加最多 3 个相关功能入口
  -> 保存回答与元数据
```

### 2.2 当前帮助知识的主要限制

`AdminHelpKnowledgeCatalog` 当前只有 17 条 PHP 数组条目。每条主要包含名称、短说明、关键词、3 个步骤、一个入口和两个追问。它适合基础导航，难以承载完整产品手册。

当前回答提示词限制为 1,200 tokens，并要求中文回答约 600 字。复杂流程容易缺少以下信息：

- 功能适用场景和目标结果。
- 依赖配置、角色权限和前置条件。
- 完整操作步骤、状态变化和结果检查。
- 系统内部逻辑、设计原则和能力边界。
- 常见失败原因、恢复方式和相关模块。
- 近期新增能力，如文章 AI 质检、标题生成运行、托管站点、Chrome 运营助手、PWA、Admin UI V3 和 CLI 0.2.0。

帮助目录内容写在代码中，后台知识库页面无法维护它。现有知识库中的官方 GEOWorkFlow 资料也没有接入 AI 工作台。

### 2.3 当前知识库已经具备的基础能力

现有知识库支持：

- Markdown、文本和 Word 导入。
- 标题、章节路径、切片策略、来源和治理元数据。
- 结构化规则切片、可选语义规划和原文稳定重建。
- Embedding、pgvector、关键词、标题和治理权重组成的混合召回。
- 向量服务不可用时的本地回退检索。
- 异步暂存、批量向量化、原子切换和失败后保留旧切片。
- 后台 Markdown 编辑器、切片预览和手动刷新。

本地运行库中已经存在 15 个知识库，其中 4 个是 2026-08 形成的 GEOWorkFlow 官方资料。它们主要服务产品介绍、部署运维、模型/RAG 和分发生态，当前 AI 工作台未读取这些资料。它们也可能已经被内容生成任务使用，因此本方案保留原资料，新增一份职责清晰的 AI 工作台系统知识库。

### 2.4 当前功能和路由规模

当前运行代码共注册 372 条路由，其中后台路由 289 条：

- 118 条包含 GET 页面或读取入口。
- 171 条包含 POST、PUT、PATCH 或 DELETE 状态变更。
- 后台主要覆盖数据分析、任务、文章、人工发布、内容资产、企业知识、URL 导入、分发、托管站点、网站设置、表单线索、AI 配置、用户权限、安全审计和系统更新。

知识库应以业务功能为章节组织，同时用路由覆盖审计确认所有后台能力都已归入某个功能章节、内部接口或受限操作。用户可点击的入口只选择稳定、只读、无需动态对象 ID 的后台 GET 页面。状态变更路由只用于核对操作覆盖，不直接输出为链接。

### 2.5 当前图片能力结论

现有普通知识库可以保存 Markdown 图片语法，但 AI 工作台无法安全显示知识图片：

- Markdown 渲染白名单没有 `img`。
- 模型输出中的 `a` 链接会转换为纯文本。
- SSE 与消息 `meta` 没有 `related_media` 字段。
- 普通知识库与知识切片没有稳定的截图关联实体。
- 知识库详情编辑器没有专用图片上传与管理流程。
- 现有图片库面向文章配图，文件通常位于公开路径，不适合承载可能包含后台界面的受保护截图。

Phase 2 需要增加一条受控的知识媒体链路。直接放开模型 Markdown 图片会扩大安全边界，也无法保证图片与问题相关。

## 3. 产品目标与验收标准

### 3.1 产品目标

1. AI 工作台能够准确解释 GEOWorkFlow 每个主要功能的用途、逻辑、流程、亮点、原理和入口。
2. 管理员可以在后台知识库中查看和维护 AI 工作台的官方知识。
3. 系统知识库在所有受支持的 Web、API 和 CLI 删除路径中均不可删除。
4. 回答中的站内入口由服务端生成，能够适配自定义后台前缀和当前管理员权限。
5. 复杂问题获得更完整的操作指南，简单问题继续保持简洁。
6. Phase 2 能根据相关章节附带可信截图，图片在刷新历史会话后保持一致。

### 3.2 Phase 1 通过标准

| 项目 | 通过标准 |
|---|---|
| 官方 Markdown | 排除 Markdown 标记、代码围栏、URL 和空白后，正文不少于 10,000 个中文汉字；可见字符目标为 20,000 至 30,000 个 |
| 功能覆盖 | 当前 289 条后台命名路由和本方案新增路由全部归类为已说明功能、内部端点、动态子页或受限操作 |
| 核心模块 | 下文内容目录中的模块全部有独立章节和入口 |
| 检索召回 | 固定评测集 Top-3 章节召回率不低于 95% |
| 入口准确率 | 固定评测集中的服务端入口准确率 100% |
| 权限 | 普通管理员无法获得超级管理员专属入口 |
| 删除保护 | Web、API、CLI 和数据库外键均阻止删除系统知识库 |
| 编辑与恢复 | 授权管理员可编辑、查看修订并恢复；保存后索引异步更新，更新失败时旧索引继续服务 |
| 回答真实性 | 评测集中虚构路由、虚构功能和虚构执行结果均为 0 |
| 多语言 | `zh_CN`、`en`、`ja`、`es`、`ru`、`pt_BR` 均完成检索和回答冒烟；事实均来自同一官方基线 |
| 延迟与降级 | 本地高置信检索不调用 Embedding；Embedding 或切片服务失败时仍能使用就绪索引或随代码基线回答 |
| 性能 | 温缓存本地检索 P95 不高于 200 ms；接入知识检索后，排除模型和网络时间的服务端首片准备 P95 增量不高于 300 ms |
| 协议兼容 | 现有会话、SSE、停止生成和历史回放继续通过 |

### 3.3 Phase 2 通过标准

| 项目 | 通过标准 |
|---|---|
| 初始截图 | 首批 24 张经过脱敏和人工检查的中文后台截图 |
| 图片相关性 | 仅在命中同一功能章节且分数达到阈值时展示，单次 0 至 3 张 |
| 图片安全 | 必须登录后台；路径穿越、外链、SVG 和未知 MIME 被拒绝 |
| 历史一致性 | 新回答和历史回答固定展示同一媒体版本，替换截图不改变历史消息 |
| 可访问性 | 每张图片具有中文标题、alt 和简短说明 |
| 语言匹配 | 首批中文截图只在 `zh_CN` 界面展示，其他语言保持完整文字回答 |
| 媒体性能 | 缩略图按需加载；文字 SSE 不等待图片文件读取，图片故障不增加正文首片等待 |
| 响应式 | 320、390、768、1280、1440 宽度无横向溢出 |
| 无图降级 | 媒体表为空、文件丢失或 Phase 2 回滚时，文字回答完整可用 |

## 4. 范围与边界

### 4.1 本次范围

- 一份 AI 工作台专用系统知识库。
- 一份随代码发布的官方 Markdown 基线。
- 一份机器可读清单，保存系统键、语言、官方版本、文件、哈希和必需章节。
- 系统知识库绑定、版本、官方哈希、自定义状态和编辑修订。
- 后台列表、详情和编辑页面的系统知识提示与删除保护。
- AI 工作台的知识检索、证据上下文、来源章节和可信导航。
- 更完整的回答策略与输出额度。
- 路由覆盖、知识质量和问答评测。
- Phase 2 的截图采集、私有存储、版本管理、章节关联、服务端选择、后台图库管理和前端展示。

### 4.2 本次不开放

- AI 工作台执行创建、修改、删除、发布、升级或外部操作。
- AI 工作台读取任意客户知识库、任务数据、文章正文或线索个人信息。
- 模型直接生成可点击站内链接、外部链接或图片标签。
- 把后台 POST/PUT/PATCH/DELETE 路由暴露成可点击操作。
- 通过截图识别自动操作后台。
- Phase 2 自动持续抓取所有页面并在生产环境中更新图库。
- 自动覆盖管理员已经二次编辑的系统知识正文。
- 首版为 5 种非中文语言制作截图包。对应界面保持文字回答，后续可按同一媒体清单扩展。
- 从任意普通知识库自动升级或按名称认领系统知识库。

现有 GEOWorkFlow 3.0 “后台帮助助手”产品边界保持不变。系统知识库负责解释和导航，执行型 Agent 仍由后续独立方案治理。

## 5. 推荐架构

```text
官方 Markdown 基线 + manifest.php
resources/knowledge/ai-workspace/
          |
          v
geoflow:sync-system-knowledge
  |  显式创建 / 安全升级 / 版本与哈希 / 提交索引
  v
system_knowledge_bases -> knowledge_bases -> knowledge_chunks
          ^                  |
          |                  +-> knowledge_base_revisions
          |
SystemKnowledgeBaseManager
  |  只读定位 / 健康状态 / 随代码基线回退
          |
          v
AdminHelpKnowledgeRetriever
  |  追问补全、本地/混合召回、章节去重、统一上下文预算
  +------------------------------+
  |                              |
  v                              v
AdminHelpAssistant        AdminHelpFeatureRegistry
  | 组织详细文字                 | 命名路由白名单、权限、图标
  +---------------+--------------+
                  v
       AdminHelpAnswerStream
       SSE delta + done metadata
                  |
                  v
       AI 工作台正文 + 章节来源 + 可信入口

Phase 2：
knowledge_media_assets + 私有不可变文件
          |
          v
AdminHelpMediaSelector -> related_media -> 前端安全图片组件
```

### 5.1 事实、导航和表现分层

系统采用三层职责：

- **事实层**：系统知识库 Markdown 和切片，保存功能说明、流程、原理、注意事项和常见问题。
- **导航层**：代码中的命名路由白名单，保存入口名称、路由名、图标、权限和稳定性。
- **表现层**：模型组织文字；服务端追加入口、来源和图片；前端只渲染经过验证的结构化字段。

管理员编辑 Markdown 可以改变回答事实和说明。管理员无法通过 Markdown 新增任意可点击 URL，也无法绕过路由权限。

#### 与 AI 工作台其他能力的集成边界

系统知识检索接入帮助回答和能力说明链路，不替代 AI 工作台已有或后续启用的意图、能力、审批和执行治理：

| 用户请求 | 主处理链路 | 系统知识库作用 |
|---|---|---|
| “任务怎么创建”“知识库有什么用” | 帮助回答 | 提供事实、步骤、原理、入口和截图 |
| “今天生成了多少文章”“渠道是否健康” | 已注册只读能力 | 提供指标口径和相关页面说明，实时结果仍来自能力处理器 |
| “启动任务”“同步设置”“发布内容” | 能力注册表、参数校验、审批和执行器 | 只解释前置条件与风险，不提供授权，也不改变执行结果 |

意图路由先决定本轮属于帮助、只读查询或执行流程。只有帮助和能力说明使用系统知识作为主要事实；能力处理器返回的实时业务数据保持最高优先级。知识正文无法新增 capability、改变风险等级、跳过审批或触发系统操作。

### 5.2 系统知识库的稳定标识与数据库保护

新增 `system_knowledge_bases` 绑定表，保持普通知识库表的通用语义：

| 字段 | 类型 | 用途 |
|---|---|---|
| `system_key` | string，主键 | 稳定定位；本项目使用 `ai_workspace_manual` |
| `knowledge_base_id` | unique foreign key | 指向现有知识库，使用 `RESTRICT ON DELETE` |
| `official_version` | string | 数据库当前采用的官方基线版本，如 `2026.08.28.1` |
| `official_content_hash` | char(64) | 判断正文是否仍等于上次采用的官方基线 |
| `customized_at` | nullable timestamp | 记录管理员是否做过二次编辑 |
| `last_synced_at` | nullable timestamp | 记录显式同步成功时间 |

`KnowledgeBase::systemBinding()` 提供关联，`isSystemManaged()` 以绑定是否存在判断。AI 工作台只按 `system_key` 查询绑定，不依赖数据库 ID、名称或排序。应用层返回友好错误，数据库外键负责最后一层删除保护。数据库高权限人员仍可先删除绑定，生产运维规范将这种操作列为受控数据变更。

### 5.3 创建、编辑和未来更新规则

`knowledge_base_revisions` 保存 `knowledge_base_id`、递增 `revision_number`、正文、内容哈希、来源类型 `official/manual/restore`、操作者、被恢复修订 ID 和创建时间。`(knowledge_base_id, revision_number)` 使用唯一约束。系统知识库名称、系统键和官方版本由清单与绑定管理，编辑页只开放正文；每次成功保存形成一条可恢复修订。

1. Schema 迁移只创建绑定表和修订表，不写入可编辑正文。
2. 新增显式幂等命令 `php artisan geoflow:sync-system-knowledge --key=ai_workspace_manual`。命令接入首次安装路径、系统更新计划的必需手工命令和部署文档，正常 Web 请求与常驻容器启动不写默认数据。
3. 系统键不存在时，命令创建新的知识库、绑定和初始修订。它不按名称认领已有知识库，避免把用户资料错误绑定成系统知识。
4. 系统键存在且当前正文哈希等于绑定表中的 `official_content_hash` 时，命令可以升级官方正文、版本和哈希，再提交切片同步。
5. 系统键存在且正文已经自定义时，命令保留管理员正文，只记录“官方更新可用”健康状态。详情页提供官方版本差异入口，首版不做自动合并。同步命令首版不提供强制覆盖自定义正文参数。
6. 授权管理员可以在差异页执行“采用当前官方版本”。该动作需要二次确认，先保存当前正文修订，再把随代码基线写成新修订，更新绑定版本与哈希并提交索引。手动编辑用于选择性吸收差异。
7. 授权管理员保存前执行字符数、必需章节和 route 指令校验。验证通过后写入新修订、设置 `customized_at`，再提交异步切片。
8. 恢复历史修订会创建一条新的修订记录，保留完整审计链。每个系统知识库保留最近 30 条修订，初始官方版本始终保留。
9. 切片采用现有暂存和原子切换机制。系统知识库同步使用 `requireRealEmbedding=false`，有 Embedding 时生成真实向量，服务不可用时仍能完成本地可检索索引。
10. 单次回答在开始时固定 `knowledge_base_id`、正文哈希、官方版本和 ready 切片来源哈希。编辑或索引切换发生在回答过程中时，本轮继续使用已固定的证据快照。
11. 索引尚未完成时，检索器对数据库正文建立缓存章节索引。数据库记录或绑定缺失时，使用随代码发布的官方基线只读回答并记录健康告警。GET 请求不负责重建数据，恢复动作由显式同步命令完成。

### 5.4 删除保护

删除保护覆盖三个层次：

- `KnowledgeBaseController::destroy()` 的后台 Web 删除。
- `MaterialLibraryService::deleteKnowledgeBase()` 的 API/CLI 共用删除。
- `system_knowledge_bases.knowledge_base_id` 的 `RESTRICT ON DELETE` 外键。

两处统一调用 `SystemKnowledgeBaseManager::assertDeletable()`。系统知识库返回明确的 409/表单错误。后台列表隐藏删除按钮并展示「AI 工作台系统知识」徽标。普通知识库继续沿用“被任务引用时不可删除”的现有逻辑。

批量删除、API、CLI 和未来新增删除入口都必须经过同一断言。架构测试扫描知识库删除调用，防止新增路径绕过。外键拦截关系型数据库中的直接知识库删除；随代码基线回退保证绑定损坏时仍有基础回答。

### 5.5 编辑权限与页面提示

- 所有管理员可以查看系统知识库详情和切片状态。
- 只有 `canManageProtectedWorkflows()` 通过的管理员可以修改系统知识库。
- 列表页显示系统徽标、用途和不可删除状态。

- 编辑页保留现有 Vditor，系统标识和版本字段不可编辑。

每轮检索规则：

8. 无直接命中时只提供总览和澄清建议，避免把所有系统知识塞入模型上下文。

为降低首轮延迟，短问题先执行本地标题、别名和关键词召回。存在精确 feature/route 别名命中，或本地最高归一化分数不低于 0.42 且领先第二名至少 0.08 时，直接采用本地结果。其余问题再启用现有向量混合召回。检索结果按“正文哈希 + 切片来源哈希 + 当前语言 + 权限范围 + 问题规范化文本”短时缓存，编辑和索引切换后自然失效。

追问解析只使用当前问题、上一条用户消息和上一轮 `knowledge_sources` 的 feature/section 标识。短追问包含“这个、它、怎么设置、然后呢”等指代词时，在检索查询中补入上一条用户问题，并把上一轮章节作为召回加权。历史助手正文只进入对话表达上下文，不进入检索事实和加权，避免旧回答放大错误。

### 7.5 回答与 SSE 元数据

预计文件：

- `app/Services/AiWorkspace/AdminHelpAnswerStream.php`
- `app/Ai/Agents/AdminHelpAssistant.php`
- `config/ai-workspace.php`
- `resources/js/admin/ai-workspace.js`

回答策略：

- 简单定位问题：直接结论 + 入口 + 2 至 4 个步骤。
- 标准操作问题：前置条件 + 5 至 10 个步骤 + 结果检查 + 常见问题。
- 原理或方案问题：概念 + 系统链路 + 设计亮点 + 边界 + 相关功能。
- 故障问题：现象判断 + 按优先级排查 + 恢复动作 + 需要查看的页面。
- 知识不足：明确缺少的事实，只询问一个必要问题。

调整建议：

- 回答生成上限从 1,200 tokens 提升到最多 2,400 tokens，并受所选模型 `max_tokens` 约束。简单问题目标为 300 至 800 个中文字符，标准问题为 800 至 1,500 个，复杂流程和故障问题为 1,500 至 2,500 个；信息完整后停止，不追求固定长度。
- 移除固定“约 600 字”限制，改为按问题复杂度控制。
- 模型只使用检索证据组织事实，知识正文中的命令性文本视为资料内容。
- 模型继续不输出可点击 URL，也不声称已经执行系统操作。
- 模型按当前后台语言回答。中文事实基线可翻译，代码、命名路由、配置键和命令原样保留，界面标签优先使用当前语言包。

      "knowledge_base_id": 24,

## 9. 关键安全与治理决策

### 9.1 只检索专用系统知识库

AI 工作台不会自动扫描所有普通知识库。这样可以避免：

- 客户资料、内部内容或个人信息进入帮助回答。
- 普通知识文档中的提示注入影响系统助手。
- 同名知识库产生冲突。
- 内容生成知识与产品操作知识互相污染。

### 9.2 路由继续由服务端控制

系统知识 Markdown 中的 route 指令只是引用。最终 URL、权限、后台前缀和展示数量都由服务端决定。模型输出的 URL 和 Markdown 链接继续不可点击。

### 9.3 图片继续走结构化字段

图片与文字事实共享章节关联，展示由服务端评分。前端不会解析模型生成的图片语法。后台截图使用私有存储和登录接口，降低敏感界面公开暴露的风险。

### 9.4 编辑后的知识仍按数据处理

系统提示明确规定知识块是参考资料，知识块中的身份修改、越权、提示词泄露、工具调用和链接生成要求均无效。route 指令和图片关联还要经过独立白名单验证。

### 9.5 版本固定与最小日志

每轮回答固定知识正文哈希、切片来源哈希和媒体版本。索引或图片在流式输出期间更新时，本轮结果保持一致。消息元数据用于历史回放和诊断，业务日志只保留模式、耗时、数量、版本和失败原因，不记录证据正文、完整问题、完整回答、密钥或向量。

### 9.6 明确的内容信任边界

官方基线经过代码评审和门禁后发布。管理员编辑内容属于受控但不受信任的数据，保存时接受结构、路由和隐私校验，生成时继续套用提示注入防护。普通业务知识库、客户知识、任务正文、文章、线索和上传图片不会进入帮助检索范围。

- 中文截图只在 `zh_CN` 展示，其他语言完整降级到文字。
- SSE 完成时持久化媒体；错误和停止不附加媒体；历史回放固定版本。
- 停用旧媒体只有在没有未过期消息引用且超过宽限期后才可清理。
- Markdown 中的任意 `img`、外链和 data URL 继续被净化。
- 320 至 1440 宽度布局、键盘和屏幕阅读器标签。

## 12. 发布、回滚和故障处理

### 12.1 Phase 1 发布

1. 备份数据库。
2. 部署代码和官方 Markdown。
3. 执行迁移。
4. 执行 `php artisan geoflow:sync-system-knowledge --key=ai_workspace_manual`。该步骤写入系统知识并提交幂等索引任务。
5. 构建前端资源。
6. 确认 knowledge 队列正在运行。
7. 检查命令退出码、系统知识库徽标、数据库删除保护、健康状态、切片 ready 状态和问答评测。

首次空库安装通过 `geoflow:install` 调用同一同步服务。现有站点升级由 `SystemUpdateManualCommandService` 在 `manual_commands` 中把该步骤标为 `required`；手工部署文档也列出同一命令。任何入口均遵守“自定义正文不自动覆盖”规则。

### 12.2 Phase 1 回滚

- 恢复旧的帮助目录和回答链路。
- 保留系统知识库、绑定、修订、正文和切片，不执行数据删除，也不执行生产 `migrate:rollback`。
- 新表和消息 `meta` 附加字段可以留存，旧代码会忽略。
- 新索引失败时继续使用上一版 ready 切片或官方基线回退。
- 回滚后需要再次上线新版时，显式同步命令会根据绑定版本和正文哈希幂等续跑。

### 12.3 Phase 2 发布

1. 执行媒体表迁移。
2. 执行 `php artisan geoflow:sync-system-knowledge --key=ai_workspace_manual --media`，导入媒体清单和 24 张私有截图。
3. 校验哈希、MIME、尺寸、route 和权限。
4. 构建前端资源。
5. 先验证文字回答，再验证有图和无图问题。

### 12.4 Phase 2 回滚

- 停止返回 `related_media` 并恢复旧前端资源。
- 保留媒体表、版本记录和私有文件，不执行生产迁移回滚。
- 旧客户端会忽略 `related_media`。
- 图片故障不会阻断正文 SSE、消息保存或相关功能入口。

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| 管理员编辑导致官方更新冲突 | 使用官方哈希和 `customized_at`；保留本地正文、记录修订并提示新版本 |
| 升级或容器启动覆盖用户正文 | Schema 迁移只建表；显式同步命令仅更新未自定义正文；普通启动和 GET 请求不写正文 |
| 切片更新失败 | 暂存和原子切换；继续使用上一版 ready 切片 |
| 回答期间索引切换 | 回答开始时固定正文和切片来源哈希，本轮始终使用同一证据快照 |
| Embedding 服务变慢 | 高置信本地召回直接返回，低置信度再调用混合召回；同步允许本地索引回退 |
| 长知识和长历史挤占模型上下文 | 24,000 字符统一预算，预留系统与问题空间，先裁剪旧历史和低分证据 |
| 知识正文新增恶意指令 | 知识块按资料处理；路由和媒体独立白名单验证 |
| 可点击入口越权 | route 存在性、稳定 GET、管理员权限三重检查 |
| 截图泄露敏感信息 | 安全样例数据、人工脱敏检查、私有存储、登录读取 |
| 图片与问题相关性差 | 章节强关联、阈值、最多 3 张、低分返回空 |
| 替换截图改变历史回答 | 文件和媒体记录不可变，消息固定媒体 ID、版本和哈希 |
| 非中文界面显示中文截图 | 媒体按 locale 精确匹配，首版非中文界面使用完整文字降级 |
| 系统知识库被误删 | UI 隐藏、Web/API/CLI 统一拦截、数据库限制删除外键和官方基线回退 |
| 未来功能新增后文档过期 | 路由覆盖门禁、更新日志核对、系统版本和官方哈希 |
| 日志扩大敏感数据面 | 只记录版本、模式、耗时、数量、哈希和失败原因，不记录证据正文与完整问答 |

## 14. 最脆弱假设

本方案假设 AI 工作台在本轮继续承担“系统帮助与导航”职责。未来如果重新开放创建、修改、发布等执行型能力，系统知识库仍可作为说明和检索来源，执行权限、参数 Schema、审批、幂等和审计必须继续由独立能力注册表和工作流引擎管理。

本方案也假设管理员二次编辑需要长期保留。未来官方版本升级会尊重 `customized_at`，由管理员决定何时吸收新版内容。产品如果要求官方内容强制同步，需要新增差异预览和合并界面。

## 15. 备选方案与取舍

### 备选 A：继续扩展 PHP 帮助目录

实现成本较低，仍然缺少后台编辑、长文知识管理、切片、版本和媒体关联。内容规模增长后维护成本会快速上升。本方案不采用。

### 备选 B：让 AI 工作台搜索所有知识库

检索范围更大，同时会引入客户资料、提示注入、同名冲突、权限和回答污染。本方案只搜索专用系统知识库。

### 备选 C：允许模型直接输出链接和 Markdown 图片

前端改动较少，权限、后台前缀、外链注入、图片相关性和历史稳定性都难以保证。本方案继续使用服务端结构化入口和媒体。

### 最小可交付版本

只实施 Phase 1。它已经满足系统知识库、不可删除、可编辑、详细问答和站内导航的核心目标。Phase 2 作为独立增强，在文字质量和检索准确率稳定后上线。

## 16. 实施顺序与确认点

### Phase 1

1. 编写官方 Markdown、机器清单、功能注册表和全量路由覆盖表。
2. 建立系统绑定、数据库删除保护、修订表和显式同步命令。
3. 完成不可删除、受控编辑、差异提示、修订恢复和知识健康状态。
4. 接入追问解析、系统知识检索、上下文预算、版本固定和可信 route 指令。
5. 调整详细回答与多语言策略，持久化精简知识来源和诊断字段。
6. 完成 72 条评测、六种语言冒烟、自动化测试和隔离浏览器验收。

Phase 1 验收通过后，系统已具备完整文字帮助能力，可以独立发布。

### Phase 2

1. 建立知识媒体表、私有存储和媒体清单。
2. 使用隔离测试浏览器采集并脱敏 24 张截图。
3. 完成不可变版本、章节、route、locale 和应用版本关联。
4. 增加后台图库管理、服务端媒体选择、鉴权读取和 SSE 字段。
5. 增加前端图库、预览、历史固定回放、留存清理和响应式验证。
6. 完成相关性、安全、隐私、语言匹配、无图降级和浏览器验收。

## 17. 最终评审结论

本方案已经锁定以下实施决策：

- 新建专用系统知识库，现有 4 个官方 GEOWorkFlow 内容知识库保持原职责。
- 系统知识库全员可查看，受保护工作流管理员可编辑和恢复修订；应用入口与数据库外键共同阻止删除。
- 官方 Markdown 与机器清单随代码发布，数据库正文用于运行和二次编辑，显式同步命令负责创建与安全升级。
- AI 工作台只检索该系统知识库。
- 站内链接使用 route 指令、全量路由分类和服务端权限白名单。
- 问答支持连续追问和六种后台语言，单轮采用 24,000 字符输入预算，回答上限为 2,400 tokens 并服从模型配置。
- 每轮固定知识正文、切片和媒体版本，保证流式回答与历史回放一致。
- Phase 2 首批制作 24 张中文后台截图，使用私有不可变存储、后台图库管理和结构化输出；其他语言首版使用完整文字回答。
- 两阶段分别验收和发布。

最终评审确认方案覆盖产品、数据、权限、安全、检索、生成、媒体、国际化、审计、留存、发布和回滚。获得实施确认后开始 Phase 1；Phase 1 完成并验收后提交 Phase 2 开始确认。
